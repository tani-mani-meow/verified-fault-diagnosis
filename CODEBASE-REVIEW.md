# Codebase Review Report

**Reviewed:** 2026-07-22T12:00:00Z
**Depth:** deep

## Summary

This review covers 32 source files across `src/`, `tests/`, and `scripts/` implementing the "Three-Certificate Trust Protocol" for acoustic-based predictive maintenance of compressor systems. The codebase is well-structured with a clear separation of concerns (ML pipeline, LLM integration, deterministic verifier, audit/simulation scripts). However, **5 critical/blocker issues** were found, including an inconsistency in verification threshold logic that could cause silent correctness bugs, a JSON parsing issue that will cause unnecessary LLM failures, and a non-existent file check in a verification script.

The three most important findings:
1. **`verifier.py`** uses different thresholds (p50 vs p75/p25) across its two verification functions for the same semantic check — claims can pass one verifier but fail the other.
2. **`pipeline.py`** shows JSON with single quotes in the LLM prompt, but `json.loads()` requires double quotes, causing unnecessary parse failures.
3. **`scripts/verify_phase1.py`** checks for `shap_summary.png` which is never generated by the pipeline.

## Critical Issues

### CR-01: Inconsistent verification thresholds across verifier functions

**File:** `src/verifier.py:116-123` vs `src/verifier.py:240-246`
**Severity:** CRITICAL

**Issue:**
`verify_claim()` (lines 116–123) uses `global_p50` as the threshold to determine if a claim "passes" for a given sample value. `check_sample_faithfulness()` (lines 240–246) uses `global_p25` and `global_p75` as boundaries for the same semantic determination. This means the two verification functions, both exported from `verifier.py`, assign different truth values to the same claim on the same sample.

**Impact:**
- `run_pipeline()` calls `check_sample_faithfulness()` (pipeline.py:318) — uses p75/p25
- `verify_explanation()` calls `verify_claim()` (verifier.py:164) — uses p50
- A value between p25 and p50 is "neutral" in `check_sample_faithfulness` but "low" in `verify_claim`. A claim of "low" passes one but fails the other.

**Fix:**
Unify the threshold logic. The p75/p25 approach used in `check_sample_faithfulness` is more appropriate for outlier detection (the stated design in the pipeline). Update `verify_claim()` to use the same p75/p25 boundaries:

```python
# In verify_claim, replace lines 116-123 with:
if value >= p75:
    passed = (claim_dir_norm == "high")
elif value <= p25:
    passed = (claim_dir_norm == "low")
else:
    passed = (claim_dir_norm == "unspecified" or claim_dir_norm == data_direction)
```

### CR-02: Prompt template uses single-quoted JSON — incompatible with json.loads()

**File:** `src/pipeline.py:202-207` (and lines 233-238, 263-268)
**Severity:** CRITICAL

**Issue:**
The system prompt template shows single-quoted JSON as the output format:
```python
"{\n"
"  'claims': [\n"
"    {'feature': 'canonical_name', ...}\n"
"  ],\n"
"  'explanation': '...'\n"
"}"
```

Python's `json.loads()` (pipeline.py:287) **requires double-quoted JSON strings**. JSON standard mandates double quotes. The LLM (Llama 3.1 70B) may faithfully follow the template and output single-quoted JSON, which will fail parsing and trigger the `unparseable` path (line 288-293).

**Impact:**
Every time the LLM copies the template format literally, the verification pipeline receives empty claims (faithfulness=0) and escalates unnecessarily. This undermines the entire trust protocol.

**Fix:**
Show valid double-quoted JSON in the prompt template:
```python
"{\n"
'  "claims": [\n'
'    {"feature": "canonical_name", "direction": "high|low", "action_critical": true/false}\n'
'  ],\n'
'  "explanation": "Technician explanation..."\n'
"}"
```

Additionally, add a JSON5 fallback or `ast.literal_eval` fallback for single-quoted strings:
```python
try:
    parsed_json = json.loads(clean_text)
except Exception:
    try:
        # Fallback: replace single quotes with double (heuristic)
        import ast
        parsed_json = ast.literal_eval(clean_text)
    except Exception:
        unparseable = True
```

### CR-03: verify_claim class_consistent logic produces false negatives for unspecified claim directions

**File:** `src/verifier.py:258-266`
**Severity:** CRITICAL

**Issue:**
In `check_sample_faithfulness()`, when a claim has an "unspecified" direction (e.g., "context_dependent", "distinctive"), the `class_consistent` check on line 266 incorrectly requires `class_dir == "neutral"`:
```python
else:
    class_consistent = (class_dir == "neutral")
```

**Impact:**
If the LLM claims a feature as "context_dependent" (deliberately not asserting high/low), but the class calibration shows the feature is "high" or "low" for that class, `class_consistent` becomes `False` and the claim is marked as `atypical`. This is semantically wrong — an unspecified claim shouldn't be inconsistent with any class direction. It should always be consistent.

**Fix:**
```python
else:
    # Unspecified claim direction is always class-consistent
    class_consistent = True
```

### CR-04: verify_claim retries non-retryable HTTP errors (4xx)

**File:** `src/llm_client.py:63-88`
**Severity:** CRITICAL

**Issue:**
The retry loop in `generate_with_usage()` uses a broad `except Exception` that catches ALL exceptions, including `requests.exceptions.HTTPError` raised by `r.raise_for_status()` on line 81. For 4xx errors (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found), retrying is pointless and wastes API quota. The code only pauses for `[429, 503, 504]` (lines 77-78) before calling `raise_for_status()`, but the raised `HTTPError` is caught by the broad `except Exception` and retried anyway.

**Impact:**
- A 401 (invalid API key) will retry 10 times with exponential backoff before failing, wasting ~17 minutes
- A 400 (bad request) will retry 10 times similarly
- The caller has no way to distinguish transient errors from permanent failures

**Fix:**
Restructure the error handling to only retry on transient errors:
```python
except requests.exceptions.HTTPError as e:
    if e.response.status_code in [429, 503, 504]:
        if attempt == max_retries - 1:
            raise
        time.sleep(delay + random.uniform(0, 1))
        delay *= 2
    else:
        raise  # Don't retry 4xx errors
except (requests.exceptions.ConnectionError, requests.exceptions.Timeout) as e:
    if attempt == max_retries - 1:
        raise
    time.sleep(delay + random.uniform(0, 1))
    delay *= 2
except Exception:
    if attempt == max_retries - 1:
        raise
    time.sleep(delay + random.uniform(0, 1))
    delay *= 2
```

### WR-06: run_faithfulness_audit.py ThreadPoolExecutor futures never checked

**File:** `scripts/run_faithfulness_audit.py:179-183` (also replicated in `run_ablation_audit.py:218-222`, `run_valuesonly_audit.py:179-183`, `run_valuesonly_pilot.py:130-134`)
**Severity:** WARNING

**Issue:**
```python
with ThreadPoolExecutor(max_workers=3) as executor:
    futures = []
    for _ in range(3):
        futures.append(executor.submit(worker))
    q.join()
```
The `futures` list is populated but never inspected. If a worker thread raises an unhandled exception (e.g., outside the try block in `audit_case`), the exception is silently swallowed because the future's `.result()` is never called. The `q.task_done()` call would also be skipped, causing `q.join()` to hang indefinitely.

**Fix:**
Add a timeout and check futures for exceptions:
```python
with ThreadPoolExecutor(max_workers=3) as executor:
    futures = [executor.submit(worker) for _ in range(3)]
    q.join()
    for f in futures:
        if f.exception() is not None:
            print(f"Worker thread failed: {f.exception()}")
```

### WR-11: download_data.py Zip Slip path traversal risk

**File:** `src/download_data.py:47,50`
**Severity:** WARNING

**Issue:**
`zip_ref.extractall()` is vulnerable to Zip Slip attacks if the archive contains path traversal entries (e.g., `../../evil.py`). While the MathWorks dataset is trusted, this is a defense-in-depth concern for a research codebase that others may fork or adapt.

**Fix:**
Add validation before extraction:
```python
for name in zip_ref.namelist():
    resolved = (extract_dir / name).resolve()
    if not str(resolved).startswith(str(extract_dir.resolve())):
        raise ValueError(f"Zip slip detected: {name}")
```
